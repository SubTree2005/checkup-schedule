# 前后端契约核对

本页记录 2026-09-01 小程序、医院管理端与 Backend 的逐项核对结果。判断标准是：页面展示的数据必须有明确来源；用户可操作的开关必须有真实执行链路；医院可配置的患者端内容必须在管理端有维护入口。

| 页面能力 | 原问题 | 修正后的单一数据源 |
| --- | --- | --- |
| 医院图片 | 小程序展示图片，医院端无法上传，数据库也无字段 | 管理端“医院设置”上传并保存到 `hospital_settings.coverImageUrl`；患者医院列表返回 `coverImageUrl/coverUrl` |
| 医院开放状态 | 患者端固定显示“正常开放” | 管理端维护 `isAvailable`；医院列表、院区选择和创建计划均使用该状态 |
| 多院区选择 | 前端生成一个虚拟院区，选择后仍可能提交机构卡片 ID | Backend 按“机构名（院区名）”分组并返回每个院区的真实 `hospitalID`；小程序提交所选院区 ID |
| 预约日期与号源 | 日期、时段和“已约人数”是前端固定数组 | `GET /api/patient/hospitals/{hospitalID}/appointment-slots` 根据开放时间、时段长度、容量和现有预约生成 |
| 预约容量 | 创建计划只校验时间在未来，伪造时间可绕过页面 | Backend 创建计划时再次校验院区开放状态、合法时段和剩余容量；满额返回 409 |
| 开始/继续重排 | 继续体检会重排，预约计划第一次开始未重排 | 第一次开始先请求 `replan`，再启动重排后的首项；继续体检由 `resume` 在服务端重排 |
| 微信消息提醒 | 页面可开启，但只有授权调用，没有后端发送任务 | 页面从 Backend 读取真实配置并在用户点击确认时申请一次性订阅；只有返回 `accept` 才随预约落库，云托管 OpenID、到期派发、失败重试和状态审计形成完整链路 |
| 系统日历 | 仅为页面概念 | 预约成功后使用小程序端 `wx.addPhoneCalendar` 写入所选院区、套餐与预约时间，不需要后端存储 |

套餐、科室、检查项目、准备要求、计划状态、排队估时、GIS 导航、历史记录和个人资料已有 Backend 接口与医院管理入口，核对后未发现页面自建第二份业务数据。订阅消息的模板 ID、字段结构、AppSecret 和派发任务均由部署环境配置；任一项缺失时页面保持禁用，不会把仅有客户端授权的状态伪装成“提醒已开启”。
