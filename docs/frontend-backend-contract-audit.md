# 前后端契约核对

本页记录 2026-09-04 对 v0.4.2 小程序、医院 Web 与 Backend 的逐项核对。页面展示必须有明确服务端来源；可操作控件必须有真实写入链路；同一业务状态只能有一个权威来源。

## 已修复

| 严重度 | 功能 | 原断点 | 当前对接方式 |
| --- | --- | --- | --- |
| 高 | 医院查看患者计划 | 患者可预约和执行，但医院 Web 只能看到汇总人数，无法定位具体患者和当前环节 | 新增 `GET /api/plans`；医院 Web 支持今日/全部、状态和患者检索，展示预约时间、套餐、进度及当前项目 |
| 高 | 今日体检统计 | Backend 按计划创建时间统计；提前创建的今日预约会漏计，今天创建的未来预约会误计 | `exam_plan.appointmentAt` 保存服务时间；预约按服务时间、现场计划按创建时间统计，列表与看板共用同一口径 |
| 高 | 排队数据源 | 医院 Web 手工填写快照，而患者进度已经在系统内，形成两个会互相覆盖的来源 | 按“全部患者使用本系统”的业务假设，从进行中计划的当前环节自动推导候检、检查中人数与容量等待；移除手工录入 |
| 中 | 平均等待 | 看板读取 `department_waiting_stats`，但三端均没有写入链路，正常使用时长期为 0 | 改为对系统内当前有患者的科室等待估算求平均；今日完成量从执行明细的实际完成时间统计 |
| 中 | 号源统计性能与一致性 | 每次查询号源都扫描状态快照 JSON，医院看板又使用另一时间字段 | 预约时间落到可索引列，号源、患者列表和看板统一读取；旧数据在启动时尽力回填 |

## 按当前业务决定暂不接入

| 严重度 | 功能 | 当前状态 | 恢复接入所需条件 |
| --- | --- | --- | --- |
| 高 | 检查报告闭环 | 小程序已具备报告展示壳，但 Backend 没有报告实体/发布接口，医院 Web 也没有录入入口；当前始终显示“未出报告” | 明确报告来源、字段规范、发布/撤回权限和审计要求后，再实现医院录入或外部 LIS/PACS 对接 |
| 中 | 医院叫号与队列回显 | 没有外部叫号数据接口；小程序明确显示当前叫号不可用 | 获得可信叫号接口后，定义号码、队列优先级、过号和多设备规则；在此之前只展示系统内估算，不伪装成现场叫号 |

## 尚需业务决策

| 严重度 | 功能 | 现状与风险 | 需要决定 |
| --- | --- | --- | --- |
| 高 | 跨患者未来资源占用 | `department_resource_calendar` 已建模，但在线 Backend 仍以单患者方式调用 Scheduler；实时队列可反映当前患者，却不能保证多个未来计划在同一设备时段绝不重叠 | 确定预约是只限制院区总号源，还是必须细分到科室/设备资源；后者需要批量排程与事务化资源预留 |
| 中 | 医院代操作患者步骤 | 医院 Web 当前只读患者计划，开始、完成、中断和结束均由患者端触发 | 是否允许医护人员代操作，以及操作角色、审计日志和误操作恢复规则 |

## 已确认对接

医院资料与图片、开放状态、多院区、预约日期与号源、套餐上下架、科室与项目约束、准备状态、患者计划状态机、GIS 导航、历史记录、个人资料、隐私同意、演示患者以及微信提醒配置均由 Backend 提供真实数据或执行链路。提醒模板、AppSecret 和派发任务属于部署配置；配置不完整时患者端保持不可用，不会伪装成已开启。
