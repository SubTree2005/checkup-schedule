# 第二版：批量滚动调度算法

## 为什么不继续使用第一版

第一版会枚举单名患者所有可能的检查顺序，适合 4–5 项检查，但检查数量增加后组合数接近 `n!`。它也没有统一管理科室设备容量，因此不能直接把 100–200 名患者的独立结果拼在一起。

第二版保留第一版代码用于小规模精确对照，新增 `build_batch_schedule` 作为大规模主入口。

## 时间约束

所有时间段均采用左闭右开区间 `[start, end)`：

- `PatientState.availability_windows`：患者可以接受检查的时间。吃饭、外出等时间直接从可用时间中扣除。
- `DepartmentState.service_windows`：科室接诊时间。设置为 `08:00–12:00`、`13:00–17:00` 后，任何检查都必须在某个区间内完整结束。
- `Exam.allowed_windows`：某项检查自身允许执行的时间。
- `Exam.earliest_start/latest_finish`：单项检查的最早开始和最晚结束时间。

算法先求这些时间段的交集，再查找能容纳完整检查时长的资源空隙，因此不会把一个检查跨过午休或排到 17:00 以后。

## 多患者和共享容量

每个科室通过 `capacity` 表示可同时工作的设备或检查位数量。算法为每个资源维护独立预约日历，任何新检查只有在以下条件全部满足时才会写入日历：

1. 患者当前没有进行其他检查；
2. 前置检查已经完成或已排在它之前；
3. 患者、科室和检查项目的时间窗存在交集；
4. 某个科室资源在完整检查时段内空闲；
5. 路程和检查时长不会导致越过时间窗终点。

## 调度策略

第二版使用带懒更新优先队列的串行调度生成算法：

1. 为每名患者寻找当前最合适的下一项检查；
2. 将候选方案放入全局优先队列；
3. 按可开始时间、剩余裕量、医疗优先级、等待公平性、步行和原方案稳定性选择一个方案；
4. 占用对应科室资源并推进该患者状态；
5. 只重新计算受到影响的患者候选，直到所有项目排完或确认无可行时段。

这是一种可解释的启发式算法，不承诺得到数学意义上的全局最优解，但避免了阶乘枚举，适合快速生成数百名患者的可执行方案。

## 动态重排

重新调用 `build_batch_schedule` 时传入上一版 `previous_schedule`：

- 距离当前时间小于 `freeze_window_minutes` 的仍然有效的项目会冻结，避免患者刚收到路线又被频繁修改；
- 如果患者临时外出、科室停机或时间窗改变导致原项目违反硬约束，则硬约束优先，该项目不会被冻结；
- 已完成和进行中的检查不会重新排序；
- 其余尚未执行项目重新进入批量调度。

后端只需从数据库读取最新患者、科室和执行状态快照，调用同一个函数，再保存返回的计划版本即可。
